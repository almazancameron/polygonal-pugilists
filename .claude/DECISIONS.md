# Architectural & Design Decisions

Durable decisions future work should respect. Not a changelog — update or remove entries that get superseded rather than layering new ones on top.

## Familiar/Combatant model is symmetric between player and enemy
`Familiar` (Resource, static build data) and `Combatant` (RefCounted, per-battle runtime state) are the same classes for both sides, with no player-specific autoload. This was a deliberate fix for a bug in the reference tutorial project, where player stats lived in a global singleton and enemy stats lived on a Resource — asymmetric, and neither wrote HP changes back to its source. Any new per-combatant state should go on `Combatant`, never on a side-specific global.

## No autoloads yet
Nothing currently needs to survive a scene change (single scene, no menu/reward loop this milestone). Introduce an autoload only when a real cross-scene need appears (e.g. the eventual round/shop loop), not preemptively.

## Turn order is Speed-driven and re-decided every exchange, not fixed alternation
`GAME_DESIGN.md` §5 leaves combat timing an open playtest question, but Speed is now the implemented turn-order driver. `battle_controller.gd` tracks `current_first_actor`; `advance_turn(actor)` only re-runs `_determine_first_actor()` once the *second* actor of the current exchange finishes (checked via `actor == current_first_actor`) — the first actor's own turn just hands off to the other side, no recompute. This is why a mid-fight Speed swing can hand one side two turns in a row (they close out an exchange as the second actor, then open the next one too) before alternation resumes. Tie defaults to the player; a `Status.grants_first_act_override()` hook lets a status force its side to open regardless of Speed, with both/neither side holding it falling back to the Speed comparison. Still an experiment per §5's OPEN/PLAYTEST status, not a locked answer — revisit if playtesting says otherwise.

## Status upkeep ticks at the start of the afflicted combatant's own turn
Not at the end of the turn that applied the status. This is an undocumented-by-design-doc call, chosen for being the more common convention and for keeping the tick next to the "is this side now allowed to act" decision. Upkeep is its own `Phase` (`ENEMY_UPKEEP`/`PLAYER_UPKEEP`) with its own pause, but that pause only plays when the side actually has active statuses — an ordinary Attack/Defend turn stays fast.

## `Status.modify_defense()` generalized to `modify_stat(stat, value)` once a second case existed
Deliberately deferred earlier (see the old version of this entry) until a real second case showed up. Fortify/Hone/Enlarge (flat/percent buffs to Defense/Power/other stats) provided it, so `modify_defense()` became `modify_stat(stat: Familiar.Stat, value: int) -> int`, dispatched through `Combatant.effective_stat()` (which `effective_defense()`/`effective_power()` both now call) rather than a defense-only path. Confirms the rule of thumb this project keeps re-deriving: don't generalize a single-case hook on spec, but don't leave it narrow once a second real case actually needs the general shape either.

## Some statuses must intercept an event, not just react to it — those go through a dedicated check, not a `Status` hook
Every hook on `Status` (`on_hit`, `on_tick`, `modify_stat`, etc.) runs *after* the event it responds to has already happened. Ward (cancel an incoming status before it's applied) and Absorption (drain a secondary pool before HP) both needed to act *during* the event instead, so they aren't implemented as overridden hooks at all — `Combatant.add_status()` and `Combatant.take_damage()` each contain a direct, hardcoded check (`get_status(WARD)`, `get_status(ABSORPTION)`) before doing their normal work. This is an intentional asymmetry, not an inconsistency: only add a new hardcoded interception point when a status genuinely needs to preempt the base flow, not merely react once it's done.

## `Technique.execute()` returns steps to run, not a combined result
`execute()` returns `Array[Callable]` (one per hit/heal/status-apply/status-modify action) instead of eagerly performing every action and returning one joined message string. `battle_controller.gd`'s `take_turn()` calls and logs each step individually, with a pause between, so a multi-hit technique reads as a sequence of distinct log lines instead of one batched turn summary. Chosen because pacing/logging is a presentation concern that belongs in `battle_controller.gd`, not baked into `Technique` itself.

## `scripts/` is organized into per-category subfolders
`scripts/status/`, `scripts/technique/`, `scripts/condition/`, `scripts/numeric_bonus/` (renamed from `damage_bonus/` once it grew beyond damage-only use, see `CONTENT_IDEAS.md`), `scripts/upgrade/` replaced a flat `scripts/` directory once each category grew enough members (20 statuses, 7 technique-related classes, etc.) that a flat listing stopped being navigable. Files not yet split into a category-specific folder (e.g. `combatant.gd`, `battle_controller.gd`) stay at the `scripts/` root — this is a folder-per-category convention, not a rule that every script needs a subfolder.

## `Condition` subclasses can check either combatant, via the same SELF/TARGET enum used elsewhere
`TargetMissingStatusCondition` and `TargetStatusStacksBelowXCondition` always read the opponent's status state, until a real need showed up for a condition that reads the *user's own* statuses (e.g. "if I'm missing Fortify, apply it"). Claude's suggestion was a new dedicated condition type; the developer instead added a `target: Target { SELF, TARGET }` field directly to the two existing classes, matching the pattern already established by `StatusApplicationAction`/`ModifyStatusAction` rather than introducing a new shape. Required a one-time migration of existing `.tres` priority-rule resources to set the field explicitly.

## Passives (`GAME_DESIGN.md` §7.3) moved from OUT OF SCOPE to CURRENT DIRECTION
Reversed the original status because the 16-familiar content pass needs each species to have its own identity beyond a stat line, and a species-bound passive is the smallest way to give it one. Not a scope-creep addition — see `GAME_DESIGN.md` §8.4/§8.5 for how it fits into the Species/Familiar/Combatant layering.

## "Defending" is now a Status, not a plain bool
`Combatant.is_defending` used to be a one-shot bool, on the reasoning that it didn't fit `Status`'s shape (consumed by the next incoming hit, not decaying over turns). Once `Status` grew an `on_hit()` hook (added for Bleed) and an `on_applied()` hook (added for Stagger), that reasoning stopped applying: `DefendingStatus` now reuses `modify_defense()`/`modify_stat()` (the same hook `AcidStatus` proved out, later generalized — see below) to double defense, and `on_hit()` to consume itself the next time its owner is hit. `is_defending` is gone from `Combatant` entirely; `Defend` is now a plain `Technique` resource with a self-targeted `StatusApplicationAction`, applying `DefendingStatus` through the normal `add_status()` path like everything else -- see the next entry for why the dedicated `DefendTechnique` subclass this used to require is also gone.

## Techniques are data, not one subclass per move
`Technique` (`Resource`) replaced the old duplicated-damage-formula button handlers. Status-applying techniques (Venom Strike, Searing Spit, Acid Bath) are a single `Technique` class built from composable `step_groups: Array[TechniqueStepGroup]`, each running a list of `TechniqueAction` subtypes (`HitAction`, `StatusApplicationAction`, `HealAction`, `ModifyStatusAction`) — *not* one subclass per move; they're the same handful of building blocks recombined with different data, and an early pass that gave each move its own subclass was corrected. (This shape replaced an intermediate single-array `status_effects: Array[StatusApplication]` design, itself already a step up from per-move subclassing — see `DEVLOG.md`'s session 4 entry for why the further rework to composable steps was needed.) Even Defend, once the one genuine subclass (`DefendTechnique`) since applying a status to *yourself* had no data-driven path, was retired the moment `StatusApplicationAction` grew a self/target field — it's just a `Technique` with a self-targeted action now. `Familiar.techniques: Array[Technique]` holds each familiar's authored moveset (Resource, not RefCounted like `Status`, specifically so it can be authored in the Inspector and later drawn from procedurally-generated pools — see `LEARNING.md`). Rule of thumb going forward: subclass when the *logic* differs; use exported fields when only the *numbers* (or *choices*, like which combatant a status targets, or which actions run in what order) differ.

## `Condition` is subclassed per kind, not parameterized by an enum
Deliberate contrast with `Technique` above: each condition kind (`TargetMissingStatusCondition`, `SelfHPBelowXCondition`, `TargetStatusStacksBelowXCondition`) reads a genuinely different fact about battle state and compares it differently — real behavioral divergence, not shared logic with different constants — so subclassing is the right call here even though it wasn't for `Technique`. `Condition` is still a `Resource` (not `RefCounted`) for the same Inspector-authoring/future-procedural-pool reasons as `Technique`.

## `PriorityRule.conditions` is an AND-array; an empty array is the catch-all
All conditions on a rule must hold for it to fire. An empty `conditions` array is vacuously true, which doubles as the unconditional catch-all case — no dedicated "AlwaysCondition" or `always.tres` resource is needed (that file was retired once this landed). `Combatant.choose_technique()` expects every `Familiar.priority_rules` list to end with such a catch-all rule so a familiar is never left with no technique chosen.

## Manual button harness is fully retired; both sides act through the same evaluator
`Combatant.choose_technique()` (walks `familiar.priority_rules` in order) is now how *both* the player and the enemy pick a technique each turn — `battle_controller.gd`'s `take_turn(actor, target, source)` replaced the old separate button-driven player path and `enemy_turn()`. There is no manual per-turn control left in the game.

## A pre-fight build-select screen exists as a deliberate stopgap, not the real buildcrafting UI
Removing manual per-turn control (above) would otherwise leave the prototype with literally nothing for the player to do, since the real replacement — an accumulating build across a run (Step 6's round/reward loop) — doesn't exist yet. `PriorityBuild` (a named, authored `Array[PriorityRule]`) plus a small button row at the start of each fight lets the player pick between pre-authored rule sets before watching the fight play out automatically. This is intentionally the smallest possible slice of buildcrafting, not a permanent feature to build further — expect it to be superseded or absorbed once Step 6's real round/reward loop exists.

## A resource referenced by more than one owner must not be edited to fit one consumer
Concrete incident: `fallback_attack.tres` is shared between Guubal's `priority_rules` and a player `PriorityBuild`. Editing it to give the player build a different fallback technique silently changed Guubal's fallback too. If a resource is genuinely shared, a build-specific need gets its own dedicated resource (see `fallback_venom_strike.tres`) instead of repointing the shared one.

## Condition blocks are authored descriptors, one per sentence *shape* — not one per `Condition` subclass
The priority builder's condition palette is driven by `ConditionBlockDefinition`/`SentencePart` `.tres` files, with a single generic `ConditionBlock` script rendering any of them. This looks like it contradicts "`Condition` is subclassed per kind" above, but it doesn't: the subclasses stay, because each still reads a genuinely different battle-state fact — the descriptors describe how to *edit* one, not how it evaluates. What justifies the descriptor layer is that `StatusComparisonCondition`, `HpComparisonCondition` and `StatComparisonCondition` are structurally isomorphic (all six of `left_target`/`compare_mode`/`right_target`/`right_value`/`comparator` plus one "which thing" field), so a table there names a symmetry the code already has rather than inventing one.

The load-bearing detail is **one descriptor per sentence shape, not per class**. `compare_mode` decides whether `right_value` or `right_target` is the live field, so a single block covering both would need slots that hide and show. Instead "target's Acid stacks < 5" and "my Poison vs their Poison" are two separate palette blocks, with `fixed_values` pinning whatever the sentence doesn't expose — which is also why `check_all` and `use_percent` need no widget at all. Adding a condition kind to the palette is then a `.tres`, not code.

Descriptors are shared and read-only; each block mints its own `Condition` via `condition_script.new()`. That is a direct application of the shared-resource rule above — a palette handing out references to shared `Condition` instances would reproduce the `fallback_attack.tres` incident at UI speed.

## Nesting condition blocks is presentation for ANDing, flattened pre-order
In the builder, dropping condition B inside condition A means "A AND B", and the tree collapses depth-first pre-order into the flat `PriorityRule.conditions` array. No `AndCondition` class exists or is needed, because an ANDed array is already what that field means. Pre-order specifically: order doesn't change *whether* a rule fires, but `choose_technique()` reports the first failing condition as its skip reason, so pre-order is what makes the reported reason match top-to-bottom reading on screen.

The one exception is a wrapper block (`body_property` set — only `NotCondition` today), whose single body child is assigned to that property and which is therefore appended *without* recursing. Recursing would also append the child unnegated, ANDing a condition alongside its own negation. A wrapper's body deliberately takes exactly one leaf condition and no further nesting: otherwise a block nested inside a NOT would flatten into the rule's array and escape the negation, so "not (A and B)" on screen would compile to "not A and B". The refusal is shown in the UI (the body names its arity) rather than merely enforced, since a silently-refused drop reads as a bug. Consequence accepted: "not (A and B)" isn't expressible, which is fine — it equals "not A or not B", and there is no OR.

## The priority editor's mock-state probe is a feature, not a debug tool
Editing HP/statuses on either side and seeing which rule wins — with every rule badged FIRES / skipped / unreached / incomplete — is required in the real editor, not just the prototype. "Unreached" is the reason: it's how a catch-all sitting above three conditional rules becomes visibly the cause of them all being dead, which is exactly the ordering mistake the editor exists to prevent. It also surfaces the catch-all requirement that is otherwise tribal knowledge in a comment on `PriorityRule`.

The probe **declares** state rather than applying it: statuses go straight onto `Combatant.statuses` instead of through `add_status()`, which would run Ward absorption and the `on_applied` hooks. A probe where entering "3 Poison" silently yields 0 because the target has Ward would be useless for reasoning about conditions — you want to state a situation, not simulate arriving at one.

Its rule walk is restated rather than read out of `choose_technique()`, because that returns `skip_reasons` as a flat `Array[String]` and badging rule *i* from `skip_reasons[i]` would couple the UI to that loop's append order. Only the loop is restated; `condition.is_met()` is the real primitive. To stop the restatement drifting, the probe also runs the real `choose_technique()` on the same compiled list and compares winners, surfacing a mismatch if they ever disagree. If `choose_technique()` is ever reworked to return per-rule results, that restatement should collapse back into it.
