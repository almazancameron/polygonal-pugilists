# Architectural & Design Decisions

Durable decisions future work should respect. Not a changelog — update or remove entries that get superseded rather than layering new ones on top.

## Familiar/Combatant model is symmetric between player and enemy
`Familiar` (Resource, static build data) and `Combatant` (RefCounted, per-battle runtime state) are the same classes for both sides, with no player-specific autoload. This was a deliberate fix for a bug in the reference tutorial project, where player stats lived in a global singleton and enemy stats lived on a Resource — asymmetric, and neither wrote HP changes back to its source. Any new per-combatant state should go on `Combatant`, never on a side-specific global.

## No autoloads yet
Nothing currently needs to survive a scene change (single scene, no menu/reward loop this milestone). Introduce an autoload only when a real cross-scene need appears (e.g. the eventual round/shop loop), not preemptively.

## Turn order is Speed-driven and re-decided every exchange, not fixed alternation
`GAME_DESIGN.md` §5 leaves combat timing an open playtest question, but Speed is now the implemented turn-order driver. `battle_controller.gd` tracks `current_first_actor`; `advance_turn(actor)` only re-runs `_determine_first_actor()` once the *second* actor of the current exchange finishes (checked via `actor == current_first_actor`) — the first actor's own turn just hands off to the other side, no recompute. This is why a mid-fight Speed swing can hand one side two turns in a row (they close out an exchange as the second actor, then open the next one too) before alternation resumes. Tie defaults to the player; a `Status.grants_first_act_override()` hook lets a status force its side to open regardless of Speed, with both/neither side holding it falling back to the Speed comparison. Still an experiment per §5's OPEN/PLAYTEST status, not a locked answer — revisit if playtesting says otherwise.

## Status upkeep ticks at the start of the afflicted combatant's own turn
Not at the end of the turn that applied the status. This is an undocumented-by-design-doc call, chosen for being the more common convention and for keeping the tick next to the "is this side now allowed to act" decision. Upkeep is its own `Phase` (`ENEMY_UPKEEP`/`PLAYER_UPKEEP`) with its own pause, but that pause only plays when the side actually has active statuses — an ordinary Attack/Defend turn stays fast.

## `Status.modify_defense()` generalized to `modify_stat(stat, value)` once a second case existed
Deliberately deferred earlier (see the old version of this entry) until a real second case showed up. Fortify/Hone/Enlarge (flat/percent buffs to Defense/Power/other stats) provided it, so `modify_defense()` became `modify_stat(stat: Familiar.Stat, value: int) -> int`, dispatched through `Combatant.effective_stat()` (which `effective_defense()`/`effective_power()` both now call) rather than a defense-only path. Confirms the rule of thumb this project keeps re-deriving: don't generalize a single-case hook on spec, but don't leave it narrow once a second real case actually needs the general shape either.

## Some statuses must intercept an event, not just react to it — those go through a dedicated check, not a `Status` hook
Every hook on `Status` (`on_hit`, `on_tick`, `modify_stat`, etc.) runs *after* the event it responds to has already happened. Ward (cancel an incoming status before it's applied) and Absorption (drain a secondary pool before HP) both needed to act *during* the event instead, so they aren't implemented as overridden hooks at all — `Combatant.add_status()` and `Combatant.take_damage()` each contain a direct, hardcoded check (`get_status(WARD)`, `get_status(ABSORPTION)`) before doing their normal work. This is an intentional asymmetry, not an inconsistency: only add a new hardcoded interception point when a status genuinely needs to preempt the base flow, not merely react once it's done.

## `Technique.execute()` returns steps to run, not a combined result
`execute()` returns `Array[Callable]` (one per hit/heal/status-apply/status-modify action) instead of eagerly performing every action and returning one joined message string. `battle_controller.gd`'s `take_turn()` calls and logs each step individually, with a pause between, so a multi-hit technique reads as a sequence of distinct log lines instead of one batched turn summary. Chosen because pacing/logging is a presentation concern that belongs in `battle_controller.gd`, not baked into `Technique` itself.

## `scripts/` is organized into per-category subfolders
`scripts/status/`, `scripts/technique/`, `scripts/condition/`, `scripts/numeric_bonus/` (renamed from `damage_bonus/` once it grew beyond damage-only use, see `CONTENT_IDEAS.md`), `scripts/upgrade/` replaced a flat `scripts/` directory once each category grew enough members (20 statuses, 7 technique-related classes, etc.) that a flat listing stopped being navigable. Files not yet split into a category-specific folder (e.g. `combatant.gd`, `battle_controller.gd`) stay at the `scripts/` root — this is a folder-per-category convention, not a rule that every script needs a subfolder.

## `Condition` subclasses can check either combatant, via the same SELF/TARGET enum used elsewhere
`TargetMissingStatusCondition` and `TargetStatusStacksBelowXCondition` always read the opponent's status state, until a real need showed up for a condition that reads the *user's own* statuses (e.g. "if I'm missing Fortify, apply it"). Claude's suggestion was a new dedicated condition type; the developer instead added a `target: Target { SELF, TARGET }` field directly to the two existing classes, matching the pattern already established by `StatusApplicationAction`/`ModifyStatusAction` rather than introducing a new shape. Required a one-time migration of existing `.tres` priority-rule resources to set the field explicitly.

## Passives (`GAME_DESIGN.md` §7.3) moved from OUT OF SCOPE to CURRENT DIRECTION
Reversed the original status because the 16-familiar content pass needs each species to have its own identity beyond a stat line, and a species-bound passive is the smallest way to give it one. Not a scope-creep addition — see `GAME_DESIGN.md` §8.4/§8.5 for how it fits into the Species/Familiar/Combatant layering.

## Rule-following passives are a `PassiveEffect` base (Trigger + Conditions + Limiter) with three payload subclasses, not one class with several mutually-exclusive fields
`GAME_DESIGN.md` §7.3 splits passives into rule-following (fits a shared shape) and rule-breaking (case-by-case, no shared scaffolding planned). **Trigger** — all twelve values are wired: `STATUS_APPLIED`/`HIT`/`ATTACK`/`BATTLE_START`/`TURN_START`/`BATTLE_END` (see history above), plus `TECHNIQUE_USED`/`TURN_END` (in `battle_controller.take_turn()`, around the technique-execution steps) and `DAMAGE_DEALT`/`DAMAGE_TAKEN` (in `Technique.apply_hit()`, scoped to direct technique hits only — not `Combatant.take_damage()` generically, since DoT ticks have no real "dealer" to attribute the trigger to). `STATUS_REDUCED`/`STATUS_REMOVED` needed the most: see `Combatant.opponent` below. **Conditions** (the existing `Condition` array, unchanged), and **Limiter** (`NONE`/`ONCE_PER_TURN`/`ONCE_PER_BATTLE`/`ONCE_PER_TECHNIQUE`, tracked per-`Combatant` in `_passive_fire_counts` since the authored `PassiveEffect` resource can be shared by many familiars) all live on the `PassiveEffect` base and are shared by every rule-following passive. What happens when triggered was first tried as two mutually-exclusive field groups on that one class, then split into real subclasses once a third payload showed up and made "several dead fields per instance" clearly the wrong shape — mirrors the existing `Condition`/`NumericBonus` subclass conventions rather than inventing a new one:

- **`OperationPassiveEffect.operation: Technique`** — a separate, reactive consequence: "deal 3 damage," "apply Ward to yourself." It's a full `Technique`, not a bare `TechniqueStepGroup` — `Technique.execute()` already runs standalone and returns the exact `Array[Callable]` shape `Combatant._fire_operation()` needs, and its `power_multiplier`/`technique_name` read naturally in the combat log. Running it does **not** cascade into the action-level ambient triggers (`HIT`/`ATTACK`/`STATUS_APPLIED`) by default — `OperationPassiveEffect.triggers_hooks` (default `false`) has to be explicitly set for a passive's own damage/status-application to also notify other reactive statuses/passives, threaded through as one `trigger_hooks` bool on `Technique.execute()`/`apply_hit()`/`apply_status()`. One bool suffices for every trigger that lives *inside* those methods (present or future) because they're all gated at the same few call sites; it does nothing for triggers that live at the turn level instead (`TECHNIQUE_USED`, `TURN_START`/`TURN_END`), which a passive's operation can never reach regardless, since nothing in `Technique.execute()` re-enters `battle_controller.take_turn()`.
- **`ModifyStatusPassiveEffect.status_effect`/`stack_bonus`** — "+1 stack applied per application." This can't be expressed as an `OperationPassiveEffect` at all: bolting a stack increase on *after* a status lands (e.g. via a hypothetical `ModifyStatusAction` ADD) would incorrectly fire `on_reapply()` on what the player experiences as a fresh application — confirmed as a real bug, not just a design smell, since it would wrongly trigger Burn's Flare or consume one of Foretell's countdown turns on a first application. Instead `Combatant.passive_stack_bonus()` is consulted by `Technique.apply_status()` *before* `Status.create()` runs, folded into the same stacks total `numeric_bonuses` already contributes to. It runs unconditionally, unlike `OperationPassiveEffect` — it's a computation input like `NumericBonus`, not part of the hooks/cascade system.
- **`ModifyStatusPassiveEffect.field_name`/`field_bonus`** — generalizes the above to any of the standardized fields the status-field-naming pass added (`BurnStatus.flare_damage`, `ForetellStatus.burst_damage`, etc.), via `Object.get()`/`set()` reflection (`field_name: StringName`, `field_bonus: float` — Godot's reflection coerces a float bonus onto an `int` target field cleanly, confirmed by test). Unlike `stack_bonus`, this is applied inside `Combatant.add_status()` itself, not `Technique.apply_status()`, and specifically *after* the merge-vs-fresh-append decision — targeting whichever `Status` instance actually survives (`existing` on a reapply-merge, the freshly-appended one otherwise), before `on_reapply()`/`on_applied()` run. This distinction matters because a Focus/passive can be gained *mid-combat*: a status already active before the passive existed must still pick up the bonus correctly when it's later reapplied. Applying the bonus to a transient pre-merge instance instead (mirroring where `stack_bonus` lives) would silently discard it on any status whose `stack_with()` doesn't happen to reference that field — which is every field except `stacks` itself, since `stack_with()` overrides only ever touch `stacks`. Compounds across repeated reapplications exactly as much as the status's own `stack_with()`/reapply logic already lets `stack_bonus` compound (e.g. Burn's `max()` merge means a stacks bonus doesn't compound there, while the default `+=` merge means it does) — not a new behavior this introduces, just the same existing variance extended to more fields.
- **`ModifyHealPassiveEffect.heal_bonus`** — "+1 heal power," structurally identical to `ModifyStatusPassiveEffect` (`Combatant.passive_heal_bonus()` consulted by `Technique.apply_heal()` before the heal amount is finalized, runs unconditionally). Deliberately its *own* class rather than a second field bolted onto `ModifyStatusPassiveEffect` — a heal bonus has nothing to do with a status, and cramming it in would just reintroduce the dead-field problem the original `PassiveEffect` subclass split was meant to fix. Originally keyed off a dedicated `Trigger.HEAL_CAST` value; migrated onto the later-added `Trigger.HEALED` instead once that existed (see below), since the two consultation paths (`check_passives()`'s reactive dispatch, restricted to `OperationPassiveEffect`/`PermanentStatPassiveEffect`; `passive_heal_bonus()`'s pre-heal computation query, restricted to `ModifyHealPassiveEffect`) filter by passive type as well as trigger and never see each other's candidates — sharing one trigger value between "reacts after a heal landed" and "adjusts a heal before it lands" is safe in practice even though it reads oddly in isolation. `HEAL_CAST` is retired (kept in the enum only because `Trigger` is append-only); nothing should be authored against it going forward.
- **`PermanentStatPassiveEffect.stat_change: ModifyStatUpgrade`** — a permanent, run-persistent stat change ("gain 5 Focus at the end of combat," "gain 1 Speed at the start of each turn"), reusing the exact resource type stat upgrades already use rather than re-deriving the stat-mutation match statement. Works because `Combatant.familiar` is the same `Familiar` object across the whole run (recreated `Combatant`s all point at it), unlike `Combatant` itself which is thrown away every battle. Distinct from a temporary buff, which is already fully expressible as an `OperationPassiveEffect` applying a Fortify/Hone-style `Status`.
- **`ModifyStatPassiveEffect.stat`/`flat_bonus`** — the "continuously-live passive" category `GAME_DESIGN.md` §7.3 had identified but left unbuilt: a permanent stat modifier with no `Trigger` involved at all, consulted directly by `Combatant.effective_stat()` right alongside every active `Status`'s own `modify_stat()` call, for as long as the passive is equipped. `trigger`/`conditions`/`limiter` are simply unused on this subclass — there's no event to gate, so nothing calls `_matching_passives()` for it. Turned out not to need the opponent-parameter signature change §7.3 had anticipated, since the first real case (a flat per-stat bonus, e.g. Focus Table tier 1's "+1 Defense") never needed to compare against the opponent's own stats. Distinct from `PermanentStatPassiveEffect`: that one fires once at a trigger and mutates the `Familiar` resource itself, persisting across battles like a stat-upgrade pick; this one is recomputed fresh every `effective_stat()` call and only applies for as long as the passive stays on the familiar.

**`Trigger.HEALED`** — fires on whoever's HP actually went up, from a direct `HealAction`, a status's `on_tick()` (Renewal), or a status's `on_hit()` (Regeneration's heal-when-hit) alike, unlike `DAMAGE_DEALT`/`DAMAGE_TAKEN` which deliberately skip DoT ticks. Needed extending into `Combatant.trigger_on_hit()` (not just `run_upkeep()`, where it was first added) once Berylazagor's Malignant Vitality needed to react to Regeneration's on-hit heal specifically, not just its tick — both paths now capture HP-before/HP-after around the relevant call and fire `check_passives(HEALED, self)` when it went up.

## Focus breakpoints are gated by tier, not by an absolute Focus value
A plain `StatComparisonCondition` (self Focus >= 5/10/15/20) would work today, but bakes each breakpoint's threshold in as a fixed number no other passive could ever touch. `FocusBreakpointCondition` (`scripts/condition/focus_breakpoint_condition.gd`) checks `tier * Familiar.focus_step_size` instead of a literal value — a breakpoint is authored as "tier 3," not "Focus >= 15." `focus_step_size` (default 5) lives on `Familiar`, read fresh every time the condition is checked. This is what makes a future passive like "your Focus breakpoints land at steps of 4 instead of 5" a one-field change (mutate `focus_step_size`, e.g. via a rule-breaking passive) that retroactively reshapes every tier's actual threshold at once, rather than needing to rewrite every breakpoint `Condition` in every `FocusTable`. Added ahead of that passive actually being built, but the addition was small enough (one `Familiar` field, one `Condition` subclass following the existing sibling pattern) that building it preemptively didn't cost much -- a judgment call, not the usual "wait for a concrete need" default.

A passive authors exactly one subclass. The trigger-fired ones share trigger/target/conditions/limiter filtering through one private helper (`Combatant._matching_passives()`, returning `PassiveEffect` matches its callers then narrow by `is` checks) so that logic isn't duplicated per payload — `ModifyStatPassiveEffect` (below) is the one exception, consulted directly with no trigger filtering at all. Focus breakpoints (§5.2) are not a separate mechanism from any of this — a breakpoint is a rule-following passive (any subclass) whose `conditions` includes a self-Focus `FocusBreakpointCondition`, authored into the shared `focus_table` (see below) rather than a familiar's own `passives`.

A real `FocusTable` (`resources/focus_tables/focus_table.tres`) now exists, referenced by every familiar's `focus_table` field — one shared table, not per-familiar/per-build data, resolving the open question `GAME_DESIGN.md` §5.2 used to carry. Four tier-gated effects currently: `ModifyStatPassiveEffect` (+1 Defense, tier 1), `ModifyHealPassiveEffect` (+1 heal power, tier 2), `ModifyStatusPassiveEffect` on Foretell's `burst_damage` (tier 3), and on Burn's `flare_damage` (tier 4). Tier 4 requires Focus 20, which no current familiar reaches — inert content, not a bug.

## `STATUS_CREATED` is the exclusive subset of `STATUS_APPLIED`, mirroring `STATUS_REDUCED`/`STATUS_REMOVED`
`STATUS_APPLIED` is inclusive — it fires whether a status was freshly created or merged onto an existing one via `stack_with()`. `STATUS_CREATED` fires *additionally*, as the more exclusive subset, only for a genuinely fresh application — same inclusive/exclusive shape as `STATUS_REDUCED`/`STATUS_REMOVED`, just for the opposite direction (gaining a status vs. losing stacks). Required `Combatant.add_status()` to change its return type from a bare `String` to `{"message": String, "created": bool}`, since it's the only place that knows whether the merge-or-fresh-append branch was taken — `Technique.apply_status()` (its one real caller) reads `created` to decide whether to check `STATUS_CREATED` passives in addition to the always-checked `STATUS_APPLIED` ones. `StaggerStatus.on_applied()`'s self-inflicted `add_status(StunStatus.new())` call already discarded the return value entirely, so it needed no change — and as a result, Stagger's self-applied Stun still doesn't notify `STATUS_APPLIED`/`STATUS_CREATED` passives at all, same pre-existing gap as before this change (that check lives in `Technique.apply_status()`, which Stagger's code bypasses). New `Trigger` values must be appended at the end of the enum, never inserted — an authored `PassiveEffect` stores `trigger` as the enum's raw integer index in its `.tres`, so inserting one would silently shift every trigger already saved after it.

## `Combatant.pre_application_snapshot` -- lets a passive check "already had this" without being fooled by the very event that's about to grant it
A plain `StatusComparisonCondition` reads *live* state, checked by `Technique.apply_status()` only *after* `add_status()` has already run — so a condition like "target already has Burn" can't tell "genuinely already burning" apart from "just started burning via this exact application," since by the time the check happens the application has already landed either way. This isn't a rare edge case: it bites any STATUS_APPLIED/STATUS_CREATED passive whose condition happens to check the same status currently being applied (found via a real authored passive, Ashwing's Ashen Down: "apply Ruin if the target is already burning" was incorrectly also firing on a fresh Burn application to a non-burning target). `Technique.apply_status()` now calls `status_target.snapshot_statuses()` into `Combatant.pre_application_snapshot` immediately before `add_status()` runs; `StatusPresentBeforeApplicationCondition` (`scripts/condition/status_present_before_application_condition.gd`) reads from that snapshot instead of live state. Deliberately a separate `Condition` subclass rather than a toggle on `StatusComparisonCondition` — the snapshot is only ever valid for the instant right after being set, so bolting this onto the general-purpose class (used everywhere, including `PriorityRule` conditions checked well outside any status application) would make it easy to silently read stale/empty data by using it in the wrong context. The dedicated class's very name signals where it's safe to use.

## A passive's `ONCE_PER_TURN`/etc. limiter is recorded before it fires, not after
`Combatant.check_passives()` calls `_record_passive_fire(passive)` *before* running `_fire_operation()`/`_fire_stat_passive()`, not after. Recording afterward is the natural order to write, but it leaves a re-entrancy window: if the passive's own operation cascades back into a `check_passives()` call for the same trigger (an `OperationPassiveEffect` with `triggers_hooks = true` whose own `trigger` is the same event type its operation produces — e.g. Ashen Down, `STATUS_APPLIED`-triggered, applying a status with hooks enabled), the limiter hasn't caught up yet and the passive can match itself again inside its own cascade. Confirmed as a real bug, not a theoretical one: a live Battabat vs. Ashwing fight stack-overflowed exactly this way. Recording first means any passive shaped like this is capped at one fire regardless of how deep its own cascade goes, with no change to normal (non-cascading) behavior.

## A passive's `ONCE_PER_TURN` window is that combatant's own upkeep *and* technique execution together
`Combatant.reset_turn_passive_limits()` is called once per actor, in `battle_controller.advance_turn()` right before that actor's upkeep begins — not at the top of `take_turn()`, which runs *after* upkeep. The two phases have to share one reset window: a passive that can be triggered by an event during upkeep (e.g. a status tick) and again by an event during that same turn's technique execution is still one turn's worth of activity, not two. Diagnosed from a real report (Ashen Down's Ruin applying twice from what looked like one Ashwing turn) — the developer correctly identified the mechanism after two wrong hypotheses from Claude, landing on "a turn is upkeep + execution together," which is now the definition this reset boundary implements.

## `Combatant.opponent` -- a stored reference to the other side, set once per battle
Added specifically to make `STATUS_REDUCED`/`STATUS_REMOVED` possible: stacks can decrease from roughly six different places (`_settle_status()`, the Ward-absorption branch in `add_status()`, `modify_status_stacks()`, the Absorption branch in `take_damage()`, and the inline expiry checks in `trigger_on_hit()`/`trigger_on_attack()`/`trigger_on_status_applied()`/`run_upkeep()`), none of which had an opponent reference available to check passives against. Threading a new parameter through every one of those signatures (and, transitively, `Status.on_applied()`, which every status subclass overrides) was the alternative — rejected as a much larger blast radius for the same result. `Combatant` is `RefCounted`, and both sides are always replaced together (`_ready()`, `start_next_round()`), so there's no window where one side's `opponent` field could outlive and reference a stale instance the way a freed `Node` can. `_notify_stack_change(status, stacks_before)` is the one shared choke point that compares a status's stacks before/after a mutation, called from every one of those six places. `STATUS_REDUCED` is inclusive — it fires on *any* decrease, whether or not the status survives it; `STATUS_REMOVED` fires *additionally*, as the more exclusive subset, when the decrease also fully expires the status. (Originally implemented as mutually exclusive — REMOVED only, never REDUCED, on a full depletion — but that meant a passive watching "any decrease" via REDUCED alone missed exactly the depletions it most wanted to react to, e.g. Absorption being fully consumed by one big hit. Caught via a real in-game report: a passive reacting to the opponent's Absorption being worn down didn't fire when a single hit happened to deplete it entirely.)

Once `opponent` existed, `check_passives()`/`passive_stack_bonus()`/`_matching_passives()`/`_fire_operation()` all dropped their own `opponent` parameter — every existing caller was already passing exactly `self`'s own opponent, so the parameter was provably redundant (and had already caused one real bug during review: a stale `_matching_passives()` comparison used `affected` where it should have used `opponent`). One canonical source of truth instead of trusting every call site to pass the right value.

## Status subclasses expose their numeric knobs as plain `var` fields with a standardized naming pattern
Prompted directly by `ModifyStatusPassiveEffect` needing something to modify: most statuses hardcoded their magnitudes as method-return constants (`BurnStatus.next_tick_damage() -> return 2`) or inline literals (`AcidStatus`'s `0.1` defense reduction, buried inside `modify_stat()`), which a passive has no way to touch. A survey of all 23 statuses found the pattern already emerging organically in the newer ones (`InfestationStatus.tick_magnitude`, `RegenerationStatus.heal_per_hit`/`heal_per_tick`, `FortifyStatus`/`HoneStatus`'s `stack_value`/`stacks_lost_per_turn`/`stacks_lost_per_hit`) — it just needed to be made explicit and applied everywhere. The standardized shape: **`stack_value`** for a buff's per-stack magnitude, **`stacks_lost_per_tick`/`stacks_lost_per_hit`** for decay rate, **`<effect>_per_tick`/`_per_hit`/`_per_stack`** for damage/heal magnitude (e.g. `PoisonStatus.damage_per_stack`, formerly baked into `next_tick_damage() -> return stacks` with an implicit `1 *`), and existing percent-shaped fields (`RuinStatus.percent_increase`) kept as their own category. All fields are plain `var`, not `@export` — `Status` instances are always constructed programmatically via `Status.create()`, never authored as their own `.tres` resource, so there's no Inspector workflow for them to serve.

One real naming collision this surfaced: `tick_magnitude` meant two different things in two different statuses (`InfestationStatus`: damage dealt *and* stacks gained per tick, by design — kept as-is; `RechargeStatus`: stacks *lost* per tick — renamed to `stacks_lost_per_tick` to match the standard). `FortifyStatus.stacks_lost_per_turn` was also renamed to `stacks_lost_per_tick` for the same reason. Neither field was `@export` or referenced by any `.tres` content, so both renames were free.

Deliberately excluded from this pass: Ward's and Stasis's 1:1 absorption/negation ratios, which live in `Combatant.add_status()`'s ward-absorption block and `Status.stacks`'s own setter respectively, not on the `WardStatus`/`StasisStatus` subclasses themselves — exposing those would mean touching shared interception logic, not one status file, and is its own separate future pass.

## Familiar sprite animation uses `AnimatedTexture`, not `AnimatedSprite2D`
Chosen over the `AnimatedSprite2D` node alternative. Confirmed via test that this requires zero code or scene changes to adopt — `Familiar.sprite` stays a plain `Texture2D`-typed field read by the same `TextureRect`-based display code either way, since `AnimatedTexture` is drop-in compatible where `AnimatedSprite2D` would need its own node and a different assignment path.

## `Familiar.passives` and `Familiar.focus_table` stay separate arrays of the same `PassiveEffect` type
Both hold `PassiveEffect`s and both execute through the identical Trigger/Operation dispatch — the split isn't about behavior today, it's about which future operations are allowed to touch each container. `passives` are individually tradeable (a future event could swap one out); `focus_table` is meant to be swapped wholesale as a named, reusable, shareable-across-familiars unit (a `FocusTable` resource) and its individual entries are never traded away on their own. Keeping them as two fields now avoids a later migration once those two operations actually need to tell the containers apart.

## "Defending" is now a Status, not a plain bool
`Combatant.is_defending` used to be a one-shot bool, on the reasoning that it didn't fit `Status`'s shape (consumed by the next incoming hit, not decaying over turns). Once `Status` grew an `on_hit()` hook (added for Bleed) and an `on_applied()` hook (added for Stagger), that reasoning stopped applying: `DefendingStatus` now reuses `modify_defense()`/`modify_stat()` (the same hook `AcidStatus` proved out, later generalized — see below) to double defense, and `on_hit()` to consume itself the next time its owner is hit. `is_defending` is gone from `Combatant` entirely; `Defend` is now a plain `Technique` resource with a self-targeted `StatusApplicationAction`, applying `DefendingStatus` through the normal `add_status()` path like everything else -- see the next entry for why the dedicated `DefendTechnique` subclass this used to require is also gone.

## Techniques are data, not one subclass per move
`Technique` (`Resource`) replaced the old duplicated-damage-formula button handlers. Status-applying techniques (Venom Strike, Searing Spit, Acid Bath) are a single `Technique` class built from composable `step_groups: Array[TechniqueStepGroup]`, each running a list of `TechniqueAction` subtypes (`HitAction`, `StatusApplicationAction`, `HealAction`, `ModifyStatusAction`) — *not* one subclass per move; they're the same handful of building blocks recombined with different data, and an early pass that gave each move its own subclass was corrected. (This shape replaced an intermediate single-array `status_effects: Array[StatusApplication]` design, itself already a step up from per-move subclassing — see `DEVLOG.md`'s session 4 entry for why the further rework to composable steps was needed.) Even Defend, once the one genuine subclass (`DefendTechnique`) since applying a status to *yourself* had no data-driven path, was retired the moment `StatusApplicationAction` grew a self/target field — it's just a `Technique` with a self-targeted action now. `Familiar.techniques: Array[Technique]` holds each familiar's authored moveset (Resource, not RefCounted like `Status`, specifically so it can be authored in the Inspector and later drawn from procedurally-generated pools — see `LEARNING.md`). Rule of thumb going forward: subclass when the *logic* differs; use exported fields when only the *numbers* (or *choices*, like which combatant a status targets, or which actions run in what order) differ.

## `Condition` is subclassed per kind, not parameterized by an enum
Deliberate contrast with `Technique` above: each condition kind (`TargetMissingStatusCondition`, `SelfHPBelowXCondition`, `TargetStatusStacksBelowXCondition`) reads a genuinely different fact about battle state and compares it differently — real behavioral divergence, not shared logic with different constants — so subclassing is the right call here even though it wasn't for `Technique`. `Condition` is still a `Resource` (not `RefCounted`) for the same Inspector-authoring/future-procedural-pool reasons as `Technique`.

## `PriorityRule.conditions` is an AND-array; an empty array is the catch-all
All conditions on a rule must hold for it to fire. An empty `conditions` array is vacuously true, which doubles as the unconditional catch-all case — no dedicated "AlwaysCondition" or `always.tres` resource is needed (that file was retired once this landed). `Combatant.choose_technique()` expects every `Familiar.priority_rules` list to end with such a catch-all rule so a familiar is never left with no technique chosen.

## Manual button harness is fully retired; both sides act through the same evaluator
`Combatant.choose_technique()` (walks `familiar.priority_rules` in order) is now how *both* the player and the enemy pick a technique each turn — `battle_controller.gd`'s `take_turn(actor, target, source)` replaced the old separate button-driven player path and `enemy_turn()`. There is no manual per-turn control left in the game.

## The pre-fight build-select screen was a deliberate stopgap, now retired
Superseded exactly as predicted when originally written: removing manual per-turn control left the prototype with nothing for the player to do until an accumulating build across a run existed, so `PriorityBuild` (a named, authored `Array[PriorityRule]`) plus a small pre-fight button row let the player pick between whole pre-authored rule sets in the meantime. Once the real reward screen (session 8) existed, this stopgap was removed outright rather than kept alongside it — a drafted familiar now just starts with its own authored default build, and the reward loop is what grows it from round 1. `scripts/priority_build.gd` and its `.tres` content are currently unreferenced; nothing else depends on them.

## A resource referenced by more than one owner must not be edited to fit one consumer
Concrete incident: `fallback_attack.tres` is shared between Guubal's `priority_rules` and a player `PriorityBuild`. Editing it to give the player build a different fallback technique silently changed Guubal's fallback too. If a resource is genuinely shared, a build-specific need gets its own dedicated resource (see `fallback_venom_strike.tres`) instead of repointing the shared one.

## Condition blocks are authored descriptors, one per sentence *shape* — not one per `Condition` subclass
The priority builder's condition palette is driven by `ConditionBlockDefinition`/`SentencePart` `.tres` files, with a single generic `ConditionBlock` script rendering any of them. This looks like it contradicts "`Condition` is subclassed per kind" above, but it doesn't: the subclasses stay, because each still reads a genuinely different battle-state fact — the descriptors describe how to *edit* one, not how it evaluates. What justifies the descriptor layer is that `StatusComparisonCondition`, `HpComparisonCondition` and `StatComparisonCondition` are structurally isomorphic (all six of `left_target`/`compare_mode`/`right_target`/`right_value`/`comparator` plus one "which thing" field), so a table there names a symmetry the code already has rather than inventing one.

The load-bearing detail is **one descriptor per sentence shape, not per class**. `compare_mode` decides whether `right_value` or `right_target` is the live field, so a single block covering both would need slots that hide and show. Instead "target's Acid stacks < 5" and "my Poison vs their Poison" are two separate palette blocks, with `fixed_values` pinning whatever the sentence doesn't expose — which is also why `check_all` and `use_percent` need no widget at all. Adding a condition kind to the palette is then a `.tres`, not code.

Descriptors are shared and read-only; each block mints its own `Condition` via `condition_script.new()`. That is a direct application of the shared-resource rule above — a palette handing out references to shared `Condition` instances would reproduce the `fallback_attack.tres` incident at UI speed.

## Nesting condition blocks is presentation for ANDing, flattened pre-order
In the builder, dropping condition B inside condition A means "A AND B", and the tree collapses depth-first pre-order into the flat `PriorityRule.conditions` array. No `AndCondition` class exists or is needed, because an ANDed array is already what that field means. Pre-order specifically: order doesn't change *whether* a rule fires, but `choose_technique()` reports the first failing condition as its skip reason, so pre-order is what makes the reported reason match top-to-bottom reading on screen.

The one exception is a wrapper block (`body_property` set — only `NotCondition` today), whose single body child is assigned to that property and which is therefore appended *without* recursing. Recursing would also append the child unnegated, ANDing a condition alongside its own negation. A wrapper's body deliberately takes exactly one leaf condition and no further nesting: otherwise a block nested inside a NOT would flatten into the rule's array and escape the negation, so "not (A and B)" on screen would compile to "not A and B". The refusal is shown in the UI (the body names its arity) rather than merely enforced, since a silently-refused drop reads as a bug. Consequence accepted: "not (A and B)" isn't expressible, which is fine — it equals "not A or not B", and there is no OR.

## The priority editor's mock-state panel plays real fights against a passive dummy, not declared HP/statuses
Rewritten from an earlier design that let the player type in an HP value and a status/stack count directly onto `Combatant.statuses`, bypassing `add_status()` entirely. That approach seemed necessary at the time to avoid Ward/Absorption silently eating a declared value, but it meant the panel could never show what a build's own passives actually do — dead weight once passives mattered. The panel now drives a real `player`/`dummy` `Combatant` pair through actual `BattleEngine.take_turn()`/`run_upkeep()` calls, one round at a time (Step/Play/Reset, plus Previous/Next once undo was added — see below), using the *currently-edited, not-yet-saved* compiled rules (a private duplicate `Familiar` whose `priority_rules` gets refreshed on every reset, mirroring the existing `_cross_check()` shadow-familiar trick below). Real resolution means Ward, Absorption, Retaliation, and DoT all behave exactly as they would in an actual fight — which is also what caught the Stasis/`_notify_stack_change()` engine bug (see below): a passive that never fired here turned out to never fire in a real battle either.

The dummy never takes its own turn by design (`engine.take_turn(user, dummy)` is the only turn call; `dummy`'s own upkeep still runs each round so its self-inflicted statuses tick). This makes any REACTIVE mechanic that depends on the *opponent acting* — Defending's `on_hit()` decay, Ward's absorb-an-incoming-status decay — permanently unable to progress in this simulator, a real, accepted limitation of testing a reactive/defensive kit against a passive target, not a bug to chase.

Three reset scopes, not one: a build edit (`segment_list.structure_changed`) restarts combatant state but keeps any custom dummy max-HP the player dialed in; the Reset button goes further and re-derives a fresh dummy from the real opponent too (discarding that custom HP); a brand new `setup()` call (a new round, a real new opponent) does the same full reset. Previous Step is a replay from scratch to `step_count - 1` rather than a snapshot/undo stack — simpler, and correct as long as the build doesn't rely on `Array.pick_random()`-style non-determinism (Cleanse and similar).

Its rule-verdict walk (✓ FIRES / ✗ skipped / unreached / incomplete) is still restated rather than read out of `choose_technique()`'s `skip_reasons`, for the same reason as before — badging rule *i* from a flat `Array[String]` would couple the UI to that loop's append order. `condition.is_met()` stays the real primitive; `_cross_check()` still runs the real evaluator on the same compiled list and flags a mismatch if it ever disagrees.

**A real, general engine bug this exposed:** `Status.stacks`'s setter redirects another status's attempted reduction into Stasis instead (the "next N reductions negated" mechanic) via `stasis.stacks -= 1`, but every caller that fires `STATUS_REDUCED`/`STATUS_REMOVED` (`run_upkeep()`, `trigger_on_hit()`, etc.) only ever notifies for the status object *it* thinks it's ticking — never for Stasis, which is the one that actually changed. Stasis's own stacks genuinely reach 0 and get erased (visible in the UI, which reads `.stacks` directly), but no passive ever hears about it. This silently made Pebbloq's Ancient Sentinel (`STATUS_REMOVED` on Stasis) dead code in every real fight, not just this panel — confirmed by reverting the fix and rerunning the round-robin: Pebbloq's win rate was 56.7% (unflagged) before the fix, 76.7% (high outlier) after. Fixed at the one place that actually has Stasis's own before-value: the interception branch itself now captures it, applies the redirect, calls `owner._notify_stack_change(stasis, stasis_stacks_before)`, and erases Stasis from `owner.statuses` if it just expired — the same notify-then-erase shape every other reduction path already follows, just finally applied to the status that's actually changing. Pebbloq needs an actual rebalance pass now that its intended kit works; not done yet.

Also required wiring `user.opponent = dummy` / `dummy.opponent = user` when the panel's Combatants are constructed — `Combatant._matching_passives()` reads `self.opponent` directly (for `trigger_target == TARGET` matching, and for evaluating *every* passive's `conditions`, regardless of trigger side), so any passive with a condition silently never matched without it. The panel had skipped this since its Combatants were never meant to fight for real under the old declare-state design.

## `HitAction` can target its own owner, not just the opponent
`HitAction.target: Target{SELF, TARGET}` (mirroring `StatusApplicationAction`'s existing field) — added for Relikarn's Grudge Strike, which deals a small amount of self-damage before its real hit. Reuses the same `Target` enum shape already established for status/stat-modifying actions rather than inventing a new one. This is what exposed the Retaliation stack-overflow below: a self-hit makes `apply_hit()`'s `user` and `target` the same `Combatant`, which a reactive on-hit status hadn't previously had to handle.

## A reactive status must guard against firing at zero stacks, even when nothing obviously calls it twice
`ThornsStatus.on_hit()` already checked `if stacks <= 0: return ""` before doing anything; `RetaliationStatus.on_hit()` didn't, because it deliberately chains into `attacker.trigger_on_hit(target)` so the counterattack can trigger the attacker's own on-hit effects (see the `Combatant.opponent` entry above) — and that chain, on a self-hit, calls back into the exact same not-yet-erased Retaliation object before the outer loop ever reaches its own erase step. Without the guard, each recursive call finds the same status (stacks already 0, but still physically in `statuses`) and chains again, unconditionally, forever — reproduced as a real stack overflow via a headless script, not `--check-only` (parse-time checks can't see this class of bug). The same latent gap could also have surfaced from two combatants both holding Retaliation simultaneously, independent of any self-hit — just never had before Relikarn existed. Fixed by adding the same guard `ThornsStatus` already had. General lesson: any status that deliberately chains back into a hook that could revisit itself needs an explicit "already spent" guard, not just correct accounting elsewhere.

## Ward only absorbs statuses someone else is applying, not the owner's own simultaneous self-applications
`Combatant.add_status(new_status, is_self_applied: bool = false)` — `is_self_applied` is computed once, at the one call site that matters (`Technique.apply_status()`, as `user == status_target`), and gates the existing Ward-absorption branch. Before this, Ward absorbed *any* incoming status regardless of source, including ones a combatant was applying to itself in the same technique cast — found via Pebbloq's Chronoparry (Defending → Ward → Stasis in one cast), where Ward immediately ate its own teammate Stasis application and expired itself before the cast even finished, which also meant Ward was never actually available to block the opponent's next real hit. `stagger_status.gd`'s self-inflicted `add_status(StunStatus.new())` call keeps the default `false` deliberately — an externally-imposed consequence of accumulated Stagger, not a voluntary self-buff, so it should still be screened by Ward same as before.

## A killing blow ends the battle before the target's own reactive on-hit statuses get a chance to run
`Technique.apply_hit()` now checks `target.is_defeated()` immediately after `take_damage()` and before letting `target.trigger_on_hit(user)`/`DAMAGE_TAKEN` fire — a hit that drops HP to 0 short-circuits straight to returning the damage message, skipping Regeneration/Thorns/Retaliation-style on-hit reactions entirely for that hit. Root cause this closes: `take_damage()` unconditionally floors `current_hp` at 0 (kept deliberately — see the overkill/Regeneration entry elsewhere in this file), but `trigger_on_hit()`'s cascade ran regardless, so Regeneration's on-hit heal could revive a combatant from HP 0 *inside the same resolution*, before `check_victory()` ever got a chance to see the kill. Without this fix, any combatant holding even one stack of Regeneration was unconditionally immune to death by direct hit, no matter the damage — confirmed via a genuine stalemate (Berylazagor vs. Mystbud, 300 turns, zero net technique damage) traced back to exactly this. Verified the fix's real-world impact by running the full round-robin with and without it before committing, since the fix also removes Regeneration's "come back from overkill within the same hit" behavior that had been explicitly kept earlier for its D&D-troll flavor — that flavor still works for a *survivable* hit (heal fires normally on any non-lethal hit), it just can no longer override an actual kill.

## Cleanse's status-strip routes through the same settle point every other stack-reduction path uses
`CleanseStatus.on_tick()` used to set `victim.stacks = 0` and erase it from `statuses` directly, bypassing `Combatant._settle_status()` entirely — meaning a Cleanse strip never fired `STATUS_REDUCED`/`STATUS_REMOVED`, unlike every other place stacks can decrease (`modify_status_stacks()`, `halve_all_statuses()`, the Ward/Absorption interception branches). Silent gap until Ignimite's Protean Purge (reacts to `STATUS_REMOVED`) needed exactly the event Cleanse produces. Fixed by having `on_tick()` call `target._settle_status(victim, victim_stacks_before)` itself, same as everywhere else — `on_tick(target: Combatant)` already receives the reference it needs.

## Absorption absorbs damage regardless of how it was computed, including `ignore_power_and_defense` hits — confirmed intended, not a bug — but is now capped at 20 stacks
`Combatant.take_damage()` applies Absorption to `amount` unconditionally before touching `current_hp`, with no distinction for damage that came from a normal power/defense-mitigated hit versus a flat `HitAction.ignore_power_and_defense = true` hit (Relikarn's self-damage, Omenfly's Portent's Toll, Berylazagor's Malignant Vitality). "Ignore power and defense" only ever meant "skip the Defense-stat mitigation formula" — it was never meant to bypass Absorption, which is a separate, universal damage-soak layer. That part is unchanged and still correct.

What *was* a real problem: Absorption had no stack cap at all, so a kit that could re-stack it faster than an opponent could chip it down built an effectively unbounded shield — the actual mechanism behind stalemates like Berylazagor vs. Ironcap. `AbsorptionStatus` now overrides both `max_stacks()` (20) and `stack_with()` (`stacks = min(stacks + other.stacks, max_stack_count)`) — mirroring the existing `AcidStatus`/`StaggerStatus` clamping convention; overriding `max_stacks()` alone does nothing, since `Combatant.add_status()`'s merge path (`stack_with()`) never consults it — only the separate `modify_status_stacks()` path does. A capped pool doesn't eliminate stalemates outright (a kit whose own refill rate never nears the cap anyway is unaffected either way), but it does guarantee any single round's cumulative incoming damage above 20 gets through regardless of how reliably the shield refills. Round-robin impact of the cap alone: Carapax 46.7%→53.3%, Ironcap 46.7%→40.0%, no other familiar's win rate moved (confirmed by diffing two runs of identical code, since Ignimite's Cleanse `pick_random()` makes its own numbers wobble a couple points between unrelated runs regardless).

## Reward selection is weighted scoring across three named slots, not binary tag filtering
`RewardSelector.pick_candidate()` scores every eligible candidate for a slot as `BASE_WEIGHT[slot] + relevance_bonus(...)` and draws via weighted random, rather than filtering candidates down by tag intersection with a fallback ladder. `BASE_WEIGHT` is a real, meaningful floor (not an epsilon), so every candidate keeps some baseline chance regardless of relevance — the alternative (a filter-then-fallback ladder) degrades badly with sparse tag data and can't express "somewhat relevant" as distinct from "irrelevant." Three slots, each with its own relevance formula: **Species** sums `familiar.species_affinities` weights for tags the candidate carries (static, never touched by what's currently equipped); **Run** sums `BuildSnapshot.owned_tag_counts` (repeated tags score higher than single occurrences) plus a role-deficiency bonus (`1.0 / (1.0 + current_role_total)` — a smooth curve, never a hard exclusion, so a glass-cannon build stays buildable); **Pivot** uses an inverted-U over combined Species+Run overlap — near-zero overlap and heavy overlap both fall back toward `BASE_WEIGHT`, peak bonus sits at moderate overlap ("a little relevant, a little strange"), on purpose contrasted with "maximum dissimilarity," which would just be random rather than adjacent-weird. `BuildSnapshot` deliberately never reads `species_affinities` — that's what keeps Species and Run capable of diverging as a run progresses instead of species identity permanently leaking into the Run slot.

`RewardSelector` takes a `Familiar` (plain authored data), a `BuildSnapshot` (plain derived data), a pool, exclusions, and an injected `RandomNumberGenerator` — no `Combatant`, no battle state, no UI, no scene tree. This is deliberate, not incidental: the explicit goal is reuse by a future AI-drafting or simulation pass without dragging in anything battle-runtime-shaped. `RewardProgression` owns round-number-to-reward-kind cadence as a separate, explicit authored array (`CADENCE`) ending in a real `RewardKind.NONE` once it runs out — `RewardSelector` itself never sees a round number at all, keeping tournament cadence and content selection as two independently-testable concerns.

## Reward-screen stat upgrades are allocate-then-confirm, never immediate-apply-per-click
Corrected mid-implementation, after the developer reviewed `assets/ui_mockup/stat_mockup.png`: each `ModifyStatUpgrade.apply()` is a one-way, run-persistent mutation, so an accidental click on the wrong stat used to mean no way back. `RewardFlowController` now stages `available_points`/`allocated: Dictionary` for one screen's invocation; `+`/`-` only mutate that staged state, and nothing touches the actual `Familiar` until a `ConfirmButton` (disabled until every point is spent) commits it all at once. Diverges from the mockup's simpler "click a row, it's applied" framing on purpose, per explicit developer instruction.

## Techniques that exist only as an `OperationPassiveEffect`'s payload live in `resources/techniques/passive_operations/`
A `Technique` used purely as a passive's internal consequence (e.g. "deal 3 damage" backing a counterattack passive) isn't structurally distinguishable from a real, player-learnable technique — nothing on the resource itself marks it as internal-only. Rather than requiring a manual cross-reference check every time `technique_reward_pool` gets curated, these live in their own subfolder so "what's eligible to offer as a reward" is answerable by folder location alone.

## Tooltip hover-tracking needs per-*meta* dedup, not just per-source-*Control* dedup
`TooltipLayer.hover_started(source, text)`/`hover_ended(source)` key everything off the source `Control`, which was fine when a source only ever hosted one possible tooltip — but a `RewardCard`'s single `description_label` can host several different status links (e.g. one card mentioning the same status three times). Hovering a second, different link on the same label used to be silently swallowed by `hover_started`'s "already showing" guard, leaving the first link's stale text and stale screen position on top indefinitely. Fixed by having each forwarder (`reward_card.gd`, `tooltip_panel.gd`) track the last meta value it forwarded and explicitly call `hover_ended()` before `hover_started()` when the hovered meta actually changes, rather than widening `TooltipLayer`'s own API to be meta-aware — `TooltipLayer` stays a generic "one tooltip per source" mechanism used by several unrelated kinds of sources (status icons, reward cards, nested tooltip links); only a `RichTextLabel`-hosting forwarder needs the finer granularity, and only it has the meta value to detect the change with.

## `TooltipLayer` cannot fully trust `RichTextLabel.meta_hover_ended`, and compensates with two independent, differently-scoped fallbacks
Confirmed via reading Godot's own engine source (not guessed at) that this is a real reliability gap, not a project-side bug: `meta_hover_ended` sometimes never fires when the cursor moves from a link to plain text within the same nested (`Button`/`ButtonGroup`-hosted) `RichTextLabel`, even though Godot's actual dispatch (`viewport.cpp`'s `gui_find_control`/`_gui_call_input`) is provably agnostic to Button-nesting. `TooltipLayer._catch_exited_active_tooltips()` runs every frame and layers two checks, from safest to most approximate: (1) has the cursor left the source control's rect entirely — always correct, since leaving the control necessarily means leaving any link inside it; (2) for a `RichTextLabel` source specifically, has the cursor drifted more than `LINK_DRIFT_TOLERANCE` (40px, tuned down live from an initial 90px) from wherever this hover began — a geometric approximation for "left the link but not the label," since there's no public API to hit-test a specific link's rendered glyphs. Both route through the existing shift-aware `hover_ended()`, not a raw removal, so shift-pinning still works regardless of which check fires. True per-glyph precision would need either a public RichTextLabel hit-test API that doesn't exist, or giving each link its own dedicated Control outside the description's single `RichTextLabel` — a bigger restructure, not attempted this pass.

## Reverse-populating the priority editor keys a Condition back to its palette definition via (script, fixed_values), not a stored back-reference
`ConditionBlockDefinition.find_matching(condition, definitions)` finds which of the priority builder's palette shapes an already-existing `Condition` instance came from by checking `condition.get_script() == candidate.condition_script` and that every one of `candidate.fixed_values`' keys reads back the same value on the condition. No schema change to `Condition` was needed (no stored "which definition made me" field) because "one descriptor per sentence shape" (see the condition-blocks entry above) already guarantees `(script, fixed_values)` is unique per definition within one palette — verified against real content, not just argued: every condition across all 16 familiars' authored `.tres` priority rules uses one of the three comparison scripts the palette covers, and one worked example was hand-traced to resolve unambiguously. `ConditionBlock.setup()` only needed one change to support this direction too: an optional `existing_condition` parameter, since its sentence widgets already initialized from the condition's live field values rather than assuming a freshly-`.new()`'d one.

Reconstructed conditions always render as a flat, top-level AND chain, regardless of how the original rule's conditions might once have been grouped in the editor — nesting is presentation only (see the flattening entry above), so a flat `Array[Condition]` cannot distinguish groupings to recover them, and no attempt is made to.

## The priority editor is now a persistent hidden sibling in `battle.tscn`, re-`setup()` every round rather than reopened fresh
Matches the existing `StatUpgradePanel`/`RewardSelectPanel` convention (always present, toggled `.visible`) rather than instantiating/freeing the scene per round. `PriorityBuilder.setup(familiar, opponent)` replaced what used to be one-shot `_ready()` logic, since the opponent (and the player's own techniques/priority_rules) differ every round — `_ready()` still calls `setup()` once too, so the scene stays independently playable standalone with its `builder_familiar`/`opponent_familiar` exports assigned directly, unchanged from session 5. Every familiar-dependent piece (palettes, the mock-state probe's `Combatant`s and its built controls, the segment list) is fully torn down and rebuilt on each call rather than diffed, since several of those pieces (`StateProbe.build_controls()`'s closures, especially) close over specific `Combatant` instances created fresh each `setup()` — leaving old controls in place after a re-`setup()` would leave them silently pointing at orphaned objects.

## Balance-testing a 16-familiar roster: a round-robin harness, then an automated local-search stat optimizer
`scripts/tools/balance_test.gd` (committed, not throwaway) runs every unordered familiar pair twice — combat is fully deterministic (with the one now-known Cleanse/`pick_random()` exception, see `DEVLOG.md`), so two runs are enough to catch the Speed-tiebreak's order-dependence without needing repeated trials. `run_round_robin(familiars: Array[Familiar])` deliberately takes a plain array rather than reaching for its own file-loader, specifically so a second script can call it repeatedly against mutated stats without duplicating the pairing loop. A throwaway stat-search script proved this out: `extends "res://scripts/tools/balance_test.gd"` (script inheritance, not duplication) reused `_load_familiars()`/`run_round_robin()` directly, then ran ~1500 trials of a greedy stochastic hill-climb — mutate one familiar's one stat by ±1 within `[2,20]` (HP `[35,85]`), keep the change only if it strictly improves a score (sum of squared deviation from a 50% win rate, plus penalties for any doomed familiar or stalemate), else revert. Real cost observed: ~1.8s per full-roster evaluation (240 battles), so "a couple thousand trials" is a genuine ~45-minute background run, not a fast operation — worth knowing before proposing this approach again. Deliberately scoped to base stats only (`power`/`defense`/`speed`/`max_hp`); it cannot fix an outlier whose real lever lives in a technique or passive field (Omenfly's Foretell-based damage ignores Power entirely, so nerfing Power there was a dead move) — those still need a manual technique/passive-level tweak.

## `PassiveEffect.describe()` composes a shared trigger phrase with each subclass's own effect phrase, mirroring `Technique.describe()`
Used to just say "executes [operation's name]" with no indication of when it fires or what it actually does — useless for a player deciding whether a passive is worth keeping. `describe()` on the base class now builds `"<name>: <trigger phrase>[, if <conditions>], <effect>."`; `_trigger_phrase()` lives once on the base (covers all twelve `Trigger` values plus `trigger_target`/`status_effect_filter` phrasing, since every trigger-driven subclass shares that half verbatim) and `_effect_phrase()` is the one thing each payload subclass overrides (`OperationPassiveEffect` delegates to a new `Technique.effect_summary()` — `describe()` minus the name/period wrapper; `ModifyStatusPassiveEffect`/`ModifyHealPassiveEffect` describe their own stack/heal bonus). `ModifyStatPassiveEffect` bypasses `_trigger_phrase()` entirely with its own `describe()` override, since it has no trigger at all (consulted directly by `effective_stat()`) and describing one would invent an event that doesn't gate anything. `trigger_target` is always rendered literally, even for triggers that are only ever checked self-referentially in practice (`HIT`/`ATTACK`/`BATTLE_START`/etc.) — a passive left at the wrong `trigger_target` for one of those is a real, silently-dead passive, and describing it as if it meant the opposite side would hide the misconfiguration instead of surfacing it.

## Player familiar + opponent lineup are randomly drawn from an authored `full_roster` export, not directory-scanned at runtime
`battle_controller.gd`'s `_randomize_matchup()` picks 5 distinct familiars (1 player, 4 opponents) at every `_ready()`, replacing what used to be a fixed Inspector-authored matchup — a lightweight stand-in for the real bracket/character-select screen (`GAME_DESIGN.md` §9.1), not the real thing (that still lets the player pick their own entrant). The first version scanned `res://resources/familiars/` at runtime via `DirAccess.list_dir_begin()`/`get_next()`, mirroring `balance_test.gd`'s own loader — this works when Godot reads the project's loose files (the editor, or a `--script` run) but silently returns an empty list against a packed, exported `.pck`, which only `balance_test.gd` never has to deal with (it's only ever run from the loose project). Result: randomization worked perfectly in the editor and produced an `Array[Familiar]` out-of-bounds crash in every exported build — confirmed by exporting and running the actual `.exe`, not guessed at. Fixed by switching to `@export var full_roster: Array[Familiar]`, authored once via the Inspector (16 entries, one per familiar), matching the convention `PriorityBuilder.block_definitions` already established for the identical reason. Each of the 5 picks was `.duplicate()`d before assignment, intending the same isolation the mock-state panel's dummy/player familiars get — `player_familiar_data`'s `priority_rules` gets mutated in place over a run, and `load()` caches `.tres` resources by path, so reusing the shared object corrupts the base familiar for any later pick of the same one within the same process. **That intent was correct but the mechanism was not**: a plain `.duplicate()` shares its Array properties with the original, so this leaked the whole time — see the `duplicate_for_run()` entry below.

Also discovered along the way, unrelated to the bug but worth knowing: this project's `export_presets.cfg` has two Windows presets — **"Windows Desktop"** (`build/FamiliarRPG_0.exe`, underscore) and **"Windows Desktop 2"** (`build/FamiliarRPG0.exe`, no underscore) — with `[runnable_presets]` mapping the *name* "Windows Desktop" to preset "Windows Desktop 2" for the editor's own Play-as-this-preset UI. The actual playtest build the developer distributes is `FamiliarRPG0.exe`, i.e. preset **"Windows Desktop 2"** — exporting via `--export-release "Windows Desktop"` silently builds the *other* one.

## Game Over screen (win or loss) replaces `get_tree().quit()`; Restart re-rolls the entire run, not just the current fight
`check_victory()` used to call `get_tree().quit()` on both the final win and any loss, closing the whole application after a 1-second delay — fine for solo dev testing, unusable for anyone else to actually play. Both branches now call `show_game_over(message)` instead, which hides the in-fight HUD (same set `begin_reward_sequence()` already hides) and shows a new `GameOverPanel`/`RestartButton`. `_ready()`'s per-run setup (matchup, `Combatant`s/`engine`, `reward_flow`, HUD visibility, opening fight) was extracted into `_start_new_run()` so `_on_restart_pressed()` can call the exact same path rather than duplicating it — per explicit developer instruction, Restart re-randomizes the matchup (`_randomize_matchup()` again, not a full-health replay of the same one), builds a *fresh* `RewardFlowController` (not just re-seeding the existing one, so reroll charges/build snapshot reset too), resets `current_round` to 0, and clears the combat log (`CombatLogView.clear()`, new). Developer-verified end-to-end: launch, get assigned a fighter, fight through the full opponent lineup with a reward/priority-editor step after each non-final win, reach the win/loss screen, and Restart into a genuinely new run — this closes the full non-bracket play loop for the first time (see `GAME_DESIGN.md` §10).

## The bracket is a tree of small Resources, not a flat array plus index math
`Bracket` holds `Array[BracketRound]`, each holding `Array[BracketMatch]` (8/4/2/1), rather than one flat 16-entry array with pairings derived arithmetically. Matches the convention `Technique`/`Condition`/`PriorityRule`/`RewardTag` already established: a small, single-purpose class per concept. The payoff is that "who do I face next," "what were the other results," and "what are this match's odds" are field reads on real objects instead of index arithmetic scattered through `battle_controller.gd` — the same reasoning that made `RewardSelector` a separate module rather than logic living in the controller.

Round-to-round advancement (`Bracket.advance_round()`) is expressed from the *source* side: walk this round's matches and write each winner forward into next round's match `i / 2`, filling `entrant_a` on even indices and `entrant_b` on odd. Written destination-first it would need the caller to know the pairing rule; written source-first the caller just says "advance this round" and the rule stays in one place.

`Bracket.generate()` copies every one of the 16 entrants via `Familiar.duplicate_for_run()`, not just the player's pick. Every entrant's build now mutates over a run (the player's through the reward screen, the AI's through `AIDrafter`), and `load()` caches `.tres` by path — sharing the base objects corrupts them for the rest of the process. See the `duplicate_for_run()` entry below for why a plain `.duplicate()` does *not* achieve this, despite what this file previously claimed. It also takes an injected `RandomNumberGenerator` rather than calling `Array.shuffle()`, which reads the unseedable global RNG; injection is what makes a seeded run reproduce the same bracket, matching `RewardSelector`'s existing convention.

## Off-screen matches are simulated for a margin, then rolled — not taken as a verdict
`GAME_DESIGN.md` §9.3 originally planned to approximate off-screen matches with a stat comparison, on the assumption that running the real engine for every one would be too expensive. That assumption was wrong: a whole run needs at most 11 off-screen matches (7 + 3 + 1 + 0), and `balance_test.gd` already measures a full headless battle at roughly 7.5ms. Maintaining a second, cruder combat model — with its own balance characteristics that could drift from the real one — would have cost more than it saved.

So `BracketSimulator.simulate()` runs the real `BattleEngine`, and its result is reduced to one number: the winner's HP fraction minus the loser's. That margin becomes an advance probability (`0.5 + 0.5 * margin`) which is *rolled against*, so a close simulated win stays genuinely uncertain and upsets remain possible — which is what §9.3 wanted the odds for in the first place. Taking the simulation as final would have removed exactly the tension the feature exists to create.

Scouting and resolving are deliberately separate calls (`BracketResolver.scout_round()` / `resolve_round()`): the player sees a match's odds before their own fight, and the outcome only after it. `resolve_round()` re-simulates rather than caching the scouted probability — the sim is deterministic for a given pair of builds and nothing about those builds changes in between, so re-deriving is free and avoids a second field on `BracketMatch` that could fall out of sync.

`BracketMatch.is_player_match` is deliberately *not* `@export`ed, unlike every other field on it: it's decided at runtime by character select and would be meaningless (and misleading) if it were ever saved into a `.tres`.

## Bracket results are read off the bracket, not narrated in the combat log
The first implementation logged each off-screen result as a combat-log line. Live testing showed those lines land at the exact moment `begin_reward_sequence()` hides the log, so the player would only ever encounter them scrolled-up during a later fight. The fix wasn't to move the lines — it was to delete them: the scouting screen lists the previous round's finished matches directly above the upcoming round, so who advanced is simply readable. A visible bracket makes narration redundant, and `BracketResolver.resolve_round()`'s return value now goes unused by the controller for that reason.

## The final boss lives outside `resources/familiars/`
`resources/bosses/final_boss_stub.tres` rather than sitting alongside the roster, because `resources/familiars/` is directory-scanned by both `scripts/tools/balance_test.gd` and `scripts/tools/bracket_test.gd`. A boss in that folder becomes a 17th bracket entrant — breaking `Bracket.generate()`'s exactly-16 requirement and quietly polluting the balance round-robin with a familiar that was never meant to be in it. The current kit is a deliberate placeholder ("The Champion", roughly doubled stats on a borrowed moveset); authoring its real kit is its own later pass.

## `Familiar.duplicate_for_run()` exists because `Resource.duplicate()` shares its arrays
`Resource.duplicate()` copies scalar properties by value but hands the copy the *same* `Array` objects the original holds. So `copy.techniques.append(...)` also grows the base resource's array — and since `load()` caches `.tres` by path, every later run in the same process inherits the previous run's upgrades. Measured, not assumed: appending to a duplicate raised the base familiar's technique count from 2 to 3, and its passive and priority-rule counts likewise, while `max_hp` (a scalar) stayed correctly isolated.

This was a **latent bug predating the bracket**. `_randomize_matchup()` used `.duplicate()` on exactly this assumption and this file documented that reasoning as if it worked; the player's own technique/passive gains had been leaking into the cached base resources across Restarts since the reward screen shipped. The bracket only made it obvious by growing all 16 familiars instead of one, which is how it finally got reported ("the upgrades that all of the familiars have accumulated aren't reset").

## Comparator/plus symbols use fullwidth and mathematical Unicode variants, not plain ASCII
yoster.ttf (the project's main font, set as the `Theme`'s `default_font`) draws plain ASCII `+`, `<`, and `>` as icon-like glyphs — a flower/cross shape for `+`, filled play/rewind triangles for `<`/`>` — not the plain symbols, confirmed by rendering the font at a large size and comparing side by side. It draws the **fullwidth and mathematical Unicode variants** (`＜ ＞ ≤ ≥`, plus the heavy-cross `✚`) plainly instead, so every comparator string and the Add Slot button's `+` now use those codepoints rather than plain ASCII — no per-widget font override needed anywhere, and no visual inconsistency with the rest of the UI.

The first fix attempt, before this was found, was a font override (`BoldPixels.ttf`) applied only to the condition-comparator dropdown widget in `condition_block.gd`. It looked complete but wasn't: `RuleSegment`'s own rule-summary line builds its comparator text independently, via each `Condition` subclass's own `describe()` (`hp_comparison_condition.gd`, `stat_comparison_condition.gd`, `status_comparison_condition.gd`, `focus_breakpoint_condition.gd`, `status_present_before_application_condition.gd`) — five separate call sites that never went through the dropdown at all. The font-override approach couldn't cover all of them without duplicating it five times; swapping the codepoints at the source fixed every one of them at once, including `stat_upgrade_row.tscn`'s unrelated `">>"` arrow (now `"→"`) and `"+"` allocate button (now `"✚"`, the developer's specific preference over a thinner `"＋"`) once that screen needed the same fix independently.

## Bold RichTextLabel text needs its own explicit `bold_font_size`, not just a `bold_font`
`yoster_bold.tres` (a `FontVariation` wrapping yoster.ttf with `variation_embolden`) makes `[b]...[/b]` spans in `tooltip_panel.gd`/`reward_card.gd`'s `RichTextLabel`s draw genuinely bold instead of relying on the underline alone, which reads as barely-there in this font — used for `Status.status_link()`'s `[url=...][b]Name[/b][/url]` wrapping. Setting only `theme_override_fonts/bold_font` rendered the bold span in a completely different, much smaller font: `RichTextLabel` tracks `bold_font_size` as its own separate theme property from `normal_font_size`/the theme's base `font_size`, falling back to the engine's own small built-in default when it's unset. Both overrides have to be set together, matched to whatever size the surrounding normal text actually uses.

## A `ScrollContainer` doesn't stretch or reposition its single child based on `size_flags`
Added defensively in an earlier session as a safety net against a recurring "content taller than its card" overflow bug (`FamiliarPanel`, `MockStateCard`, etc. in the priority builder). It does absorb *vertical* overflow the way intended, but it does **not** treat its child as a normal `Container` child for sizing/alignment purposes: the child sits at its own natural minimum size, always anchored to the `ScrollContainer`'s top-left corner, regardless of `size_flags_horizontal`. This silently broke two things this session before the pattern was recognized — the prefight screen's opponent card couldn't be end-aligned (portrait meant to sit flush against the card's right edge instead sat wherever the natural-minimum-width content landed near the left), and the stat-upgrade screen's technique/passive lists collapsed to their own tiny natural minimum (~96px) inside a much wider available card, wrapping technique names mid-word.

The fix both times was the same: once real content sizes are confirmed to comfortably fit the card (verified via `get_combined_minimum_size()` against the card's actual `.size`), remove the `ScrollContainer` and use a plain anchored `Container` instead — full-rect anchors make it actually fill the available space, and ordinary `HBoxContainer`/`VBoxContainer` expand/fill flags then work exactly as expected. Reserve `ScrollContainer` for cases where vertical overflow is a genuine, still-open possibility, and don't expect it to also solve horizontal alignment or fill-to-width in the same breath.

## The familiar identity card (name + portrait + stat list with an `HPBar` for Max HP) is duplicated three times, not shared
The priority builder's `FamiliarCard`, the prefight screen's player/opponent cards, and the stat-upgrade screen's left column all show the same shape — a colored name, a portrait in a dark spotlight frame, and icon/label/value stat rows with Max HP rendered as an actual small `HPBar` instead of a plain number — each via its own ~50-line `_populate_fighter_card()`-shaped function in that screen's own controller script, not a shared component. Deliberate, not an oversight: each screen owns a different Control subtree shape around the card (the priority builder's needs a `ScrollContainer`-turned-plain-`VBoxContainer` wrapper for its own reasons, the prefight screen mirrors left/right, the stat screen sits inside a three-column layout with completely different siblings), so a shared scene would need its own configuration surface for all of that anyway. `Familiar.stat_icon()` — the one piece with zero context dependency, a pure `Stat -> Texture2D` lookup — *was* extracted (next to the existing `stat_name()`) once a third independent copy of the same dict showed up; the full card-building logic wasn't, since three call sites each shaped by a different surrounding layout didn't converge the way the icon dict did.

The fix is deliberately **not** `duplicate(true)` (deep). That would give each copy its own `Technique`/`PassiveEffect` instances, and `RewardSelector` decides "do I already own this?" by identity against the shared content pool (`excluded_content: familiar.techniques`) — deep copies would never match a pool entry, silently making every already-owned item re-offerable. `duplicate_for_run()` takes the middle ground: a plain `duplicate()` for the scalars, then fresh `Array.duplicate()` copies of `techniques`/`priority_rules`/`passives`/`species_affinities` holding the *same* element references. Mutating the arrays is isolated; identity comparisons still work.

`state_probe.gd`'s plain `.duplicate()` is correct and deliberately left alone: it only ever *reassigns* `priority_rules` (replacing the reference wholesale) and sets scalar `max_hp`, never mutates an array in place. Assignment is safe; in-place mutation is not. That distinction is the whole rule.

`scripts/tools/bracket_test.gd` now guards this (`entrants_are_isolated_from_base_resources`), verified by reverting the fix and watching it fail on all four assertions before restoring it.
