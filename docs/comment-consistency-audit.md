# Comment consistency audit

Completed 2026-09-09 against `88775f3` plus the comment cleanup in this working tree.

Scope: first-party GDScript comments, traced through their callers and relevant authored resources. Documentation and recent history supplied context; neither was treated as proof of runtime behavior. Addon/vendor comments were outside scope. This is a findings list and replacement plan, not approval to change game semantics.

## Changes made

Removed straightforward narration, abandoned commented-out code, and duplicated explanation in ten scripts. Examples include the abandoned `first_act_override` branch, a second copy of the upkeep-history rationale, a conditional bonus's line-by-line description, and UI helper descriptions that repeat their bodies. Shortened allocation commentary while preserving the important distinction between staged allocations and committed Familiar changes.

Kept useful explanations of resource identity, Stasis recursion guards, fresh-status notification ordering, numeric-bonus sharing, layout constraints, tooltip workarounds, and authored content discovery. Inaccurate comments below remain in place for the requested replacement review. No executable statements, authored resources, scenes, or gameplay strings were changed.

## Validation and limits

Godot 4.7.1 headless runtime probes completed **18/18 checks, zero failures**. They covered overkill reporting, flat-hit base, healing's Defense operand, Lifesteal fraction, Burn merge, field accumulation, Focus modifier gating, optional learned-technique rules, shallow/run-copy identity, reference-cycle retention/release, StepGroup gate timing, condition aliasing, probe reset accumulation, cross-check incompleteness, bracket mutation, and the HP-margin formula. These are current-behavior checks, not assertions that the behavior is desirable. The margin check exercised the formula, not a complete stalemated fight.

The existing bracket harness completed **12/12 checks**. Its passing non-mutation fixture does not cover the permanent-stat passive counterexample. Command:

```powershell
& '../Godot_v4.7.1-stable_win64_console.exe' --headless --path . --log-file "$env:TEMP/pp-comment-bracket-test.log" --script res://scripts/tools/bracket_test.gd
```

Runs emitted resource-UID fallback warnings, root-certificate/MCP registry diagnostics, and shutdown leak diagnostics. Thus these are completed behavioral checks, not warning-free startup/shutdown validation. The temporary audit script was removed; its runtime output is in the session's temporary `pp-comment-audit.log`. No full visual playthrough or new balance CSV generation was needed for comment-only edits. Static UI findings above concern direct code/comment contradictions; they do not establish visual usability.

## Replacement and follow-up plan

1. **Correct obsolete references and ownership descriptions.** Replace retired fields/functions, panel ownership, boss/character-selection/reward-flow history, and layout terminology. Keep historical reasons only where they explain a constraint still present.
2. **Replace incorrect contracts with concise current-behavior descriptions.** Prioritize damage returns, StepGroup timing, hook scope, status merging/modification, optional priority rules, and weighting. Use concrete exceptions instead of “always,” “exactly,” or “safe” where the code does not guarantee them.
3. **Label behavioral discrepancies before fixing them.** Resource aliasing/lifetime, preview reset fidelity, simulation mutation, RNG/scouting consistency, and cross-check completeness need separate reviewable fixes. Do not change the code simply to make an old comment true.
4. **Resolve design-dependent documentation separately.** Confirm intended healing calculation; conditional continuous Focus modifiers; whether previews/scouting must isolate all run growth; whether resolution must use the exact scouted odds; whether stalemates should force close odds; and how learned AI techniques should acquire priorities. These answers materially affect behavior, so this audit does not choose them.
5. **Validate replacements as comments only.** Compare executable lines against the baseline. For any subsequently approved behavior fix, retain a focused regression fixture for its counterexample and run the affected simulation/UI flow.

Two related findings are not inaccurate source comments: ModifyStatPassiveEffect already says its conditions are ignored, although the authored Focus Defense effect has a condition; and healing tooltip text describes “damage dealt” even though healing computes a separate subtractive value using the opponent's Defense. Those are implementation/content/design or player-facing text conflicts and were left unchanged.
